# 文件維護規範 (Docs Guide)

> 返回 [文件總覽](README.md)
>
> 本檔是這個專案**文件本身的規則書**：各文件的職責分工、新內容該寫哪、
> 怎麼記錄、怎麼封存、怎麼處理過期。**要新增／修改任何文件之前先看這裡。**
> （架構仿公司專案的 docs-maintenance 機制，2026-08-21 建立。）

---

## 一、職責分工（一份內容只有一個家，其他地方指過去）

| 文件 | 職責 | 鐵則 |
|---|---|---|
| `/AGENTS.md` | AI 工作契約：常駐鐵則＋動工前必讀路由表＋指路。 | **保持薄**：細節住在 readme/，這裡只指過去、不貼內文 |
| `/CLAUDE.md` | 鏡像入口，`@AGENTS.md` 匯入。 | **永不加內容**（包括 `/init`） |
| `readme/README.md` | 文件地圖：每份主題文件「內容＋什麼時候讀」的表。 | 只放地圖與接手提示；**不寫日期流水帳**（那是 PROGRESS 的事） |
| `readme/PROGRESS.md` | 變更日誌：做過什麼、怎麼演進、當時為什麼難。 | **倒序（最新在最上）**；歷史條目**永不改寫**，只封存 |
| `readme/PROBLEMS.md` | 踩坑記錄：症狀→原因→解法。 | 編號**永不重編、永不重用**；淘汰的條目封存留存根 |
| `readme/TODO.md` | 缺口清單：半成品、暫缺、待拍板。 | 分節＋建立日期；**新節加檔尾**；整節完成才搬走 |
| `readme/<主題>.md` | 各系統的**現狀**說明（唯一真相）。 | 只寫「現在是怎樣」；歷史演進寫 PROGRESS，別堆在主題文件裡 |
| `readme/DOCS_GUIDE.md` | 本檔：文件的規則。 | — |
| `readme/archive/` | 封存區：不再代表現況的文件與搬出的歷史條目。 | **原文照錄、非當前真相、不作開發依據**；`archive/README.md` 是封存原因表 |

**發現兩份文件寫同一件事** → 依上表選一個家留著，另一份改成一行指路。

## 二、新內容該寫哪（決策樹）

1. 每次動工都要遵守的規則／踩了會出大事的路由？ → `/AGENTS.md`（保持薄）。
2. 完成了一個功能／修了一個非顯而易見的 bug？ → `PROGRESS.md` 新條目（格式見下）。
3. 踩到新坑（症狀→原因→解法）？ → `PROBLEMS.md`，放進所屬分類、編號接該分類最大號。
4. 某系統「現在是怎樣」的說明？ → 對應主題文件；沒有的話**先想清楚再開新檔**，開了就要進 README.md 文件地圖。
5. 半成品缺口、之後再補、待拍板？ → `TODO.md` 檔尾新節。
6. 文件不再代表現況？ → **封存，不刪除**（見第五節）。

**寫之前自問**：這句話一年後還對嗎？「現狀」寫主題文件；「這次發生的事」寫 PROGRESS；
「會重踩的坑」寫 PROBLEMS。三個地方都寫到同一件事時，內文只留一份，其他兩處指路。

## 三、真相階層（查證時先問「哪個證據能回答這句話」）

文件、註解、記憶都可能過期，**寫得再肯定也不能升格為真相**。分類找對證據：

| 陳述類型 | 最權威的當前證據 |
|---|---|
| 遊戲行為／流程 | 實際程式碼路徑（`DipanProj_Main/Assets/Scripts/`），能重現就重現 |
| 表格欄位／數值 | **CSV 檔本身**（`Assets/Data/*.csv`、MapsTable 等）——欄位序號以 CSV 為準，不信文件 |
| 地圖資料 | `.dipanmap` 檔與 `catalog.json` 本身 |
| 檔案／類別存不存在 | 檔案系統＋全域搜尋（含呼叫端，證明它是活的） |
| 編輯器行為 | `DipanProj_MapEditor/Assets/Scripts/` 的程式碼 |
| 歷史脈絡（當時為什麼這樣做） | PROGRESS／archive 的當日條目（它們是快照，**不代表現況**） |

**修正文件錯誤的閉環**：① 把可證偽的那句話寫下來、搜出所有重複處 → ② 用上表求證
→ ③ 改「擁有這份內容的家」，其他處改指路 → ④ 用舊字串全域掃一遍抓殘留 → ⑤ 重讀改過的整份檔案。
**沒查證過的不要寫**；查不到的標明「未確認」，別編一個看起來完整的說法。

## 四、PROGRESS 記錄格式

一條 = 一則 `* [x]` 開頭的獨立條目，加在**檔案最上方註記之下**（倒序）：

```markdown
* [x] **標題：這次交付了什麼**（YYYY-MM-DD，見 [相關文件.md](相關文件.md)、[PROBLEMS.md](PROBLEMS.md) **編號**）：
  一段話講清楚改了什麼、為什麼。<br>**某個坑或決策的小標**：脈絡→結論；坑要寫「為什麼會踩到」
  與「試過什麼、為什麼不行」。<br>**通則**：把坑泛化成下次可複用的規則——這是整條記錄最值錢的部分。
```

- **記錄的價值在坑與通則，不在流水帳**——改了哪些檔 commit 都有，這裡要寫的是 diff 看不出來的事。
- 同一輪工作的多個子題寫進**同一條**（各自一個粗體小標），不拆成多條。
- 條目寫完就定稿；**歷史條目永不改寫**——後來推翻了就寫一條新的，註明推翻哪一條（前例：出生點 startFlag）。
- 規則若已寫進主題文件或 AGENTS，這裡留一句話＋指路即可，不重複全文。

## 五、封存規則（封存＝搬家，不是刪除）

**通則：原文照錄、原位留索引或存根、`archive/README.md` 登記一行原因。任何紀錄都不准直接刪除。**

| 對象 | 觸發條件 | 做法 |
|---|---|---|
| `PROGRESS.md` | 檔案超過 **~96KB** | 把**最舊**條目原文搬到 `archive/PROGRESS-archive.md`（正序），直到正檔回到 **~64KB** 以下；archive 檔頭的逐條索引同步補上 |
| `PROBLEMS.md` 條目 | 情境已淘汰（機制整個換掉、坑不再可能發生） | 整則原文搬 `archive/PROBLEMS-archive.md`；**原位留存根**（保留編號＋一句話說明為何淘汰＋指向封存處）；編號永不重用 |
| `TODO.md` 節 | 整節全部完成 | 整節原文搬 `archive/TODO-done.md`（沒有就建）；節內個別打勾項留在原節當脈絡 |
| 整份主題文件 | 不再代表現況、被新文件取代 | 檔頭加封存 banner（何時封存、為何、現況看哪）後搬進 `archive/`；**仍有效的內容先萃取進活文件**；**同一次改動更新所有指向它的連結**（README 地圖、AGENTS、其他文件） |

封存是**大小與真實性驅動**，不是年齡驅動——條目再舊，只要還是現況的一部分就不搬。

## 六、過期文件的處理

- 發現文件與現況不符：**小錯當場修**（依第三節查證後改）；**大範圍過期先在檔頭（或該節開頭）加 ⚠ 過期標示**，
  寫明「哪部分過期、現況以什麼為準」，之後再排時間逐段修正。**絕不默默留著誤導下一個人。**
- 自己的改動讓某文件過期 → **同一次改動裡把它改對**，這是改動的一部分，不是之後的待辦。
- 最危險的過期是「**有預設值所以不會報錯、照著寫只會默默錯**」的範例碼（前例：`SetBloodline` 單參數會靜默重設
  BodyScale）——修文件範例時要實際對照現在的函式簽名。

---

## 七、大改文件後的收尾檢查

1. 全 readme 的 `.md` 相對連結零斷連（含 archive/）。
2. 被引用的 PROBLEMS／PROGRESS 編號全部存在（存根也算存在）。
3. 搬移過的內容逐條與原文比對一致（原文照錄）。
4. 用「舊講法的關鍵字」全域掃描，抓沒改到的殘留。
5. README.md 文件地圖與實際檔案清單一致（新檔有列、封存檔已移到 archive 列）。
